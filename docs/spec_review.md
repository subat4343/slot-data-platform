# 要求仕様の整合性レビューと未決定事項

対象: `claude_code_slot_master_spec.md`（初期要求仕様）。レビュー日: 2026-10-21。

重大度: **高** = 仕様どおりに進めると実装・運用が成立しない / **中** = 解釈を固定しないと実装が揺れる / **低** = 補足・明確化。
対応欄の ADR は `docs/decisions/` を参照。

## 1. 整合性レビュー（矛盾・不足と解消方法）

| # | 重大度 | 指摘 | 解消方法 |
|---|---|---|---|
| R1 | 高 | 初期収集対象 2 サイトとも、利用条件上、自動取得が認められていない。P's CUBE は約款 第5条(1)(2) で自動取得と HTML 抽出を禁止。台データオンラインは robots.txt で台・店舗の詳細系パスを全 UA に Disallow し、規約 第4条10号でデータベースの複製を禁止 | 仕様 §1 の「利用不可の場合は収集を止め、手動インポートを代替とする」を適用した。アダプターは許可ゲート付きで実装し、`automated_fetch: permitted` と許可の根拠が設定されない限り起動しない。手動インポート経路（JSON/CSV）を本番経路とした（ADR-0002、`source_contracts.md`） |
| R2 | 高 | §4.1 `halls` に店舗コード列が無いが、§7 の配置 CSV は `hall_code` で店舗を指定する | `halls.code TEXT UNIQUE NOT NULL` を追加（ADR-0005） |
| R3 | 中 | §3.2「未公開・取得失敗・解析不能・未確定・真のゼロを区別」とあるが、§4.3 `daily_machine_stats` は数値列のみで、NULL の理由を保持できない | 値ごとの状態を `field_status JSONB` に保持する。観測側は `field_metadata` に状態・原文・ラベル・単位・出自を保持（ADR-0006） |
| R4 | 中 | §6-8 の `provisional -> final_candidate -> final` の遷移根拠が未定義。§4.1 に閉店時刻が無い | `halls.closing_time` を追加した。閉店前は provisional、閉店後は final_candidate とし、同一取得元で同じ値が `settle_hours`（既定 24h）以上続いたら final とする。訂正は `is_corrected` フラグで表す（ADR-0007） |
| R5 | 中 | §5-2 の採用ルール（優先順位・鮮度・完全性・品質・確認状態）の適用順が未定義 | v1 の順序を「確定段階 > 取得元優先度 > 品質 > 完全性 > 鮮度」と定め、改訂履歴に `selection_rule_version` を記録（ADR-0008） |
| R6 | 中 | §9 の品質課題（理由コード・重大度・対象・検出日時）と手動訂正（監査可能な訂正レコード）の格納先テーブルが §4 に無い | `data_quality_issues` と `manual_corrections` を追加。`daily_stat_revisions.source_observation_id` は NULL 可とし、手動訂正の根拠 `manual_correction_id` を追加（CHECK でどちらか必須） |
| R7 | 中 | §5-5「同一原本・同一パーサー版の重複解析を防ぐ」と §4.2「同一内容でも取得イベントの存在は保持」の両立方法が未定義 | 取得イベントは毎回 `raw_payloads` に記録する。同一内容（店舗・取得元・SHA-256 が同じ）は `duplicate_content` として初回原本を参照し、解析しない。解析は `UNIQUE(raw_payload_id, parser_name, parser_version)`。同一内容の再取得時刻は final 判定の根拠に使う |
| R8 | 中 | §7「角・角2は物理的な列端から算出し、途中の空きや通路を考慮」の具体規則、「向かい」の算出根拠が未定義 | 通路・柱は列を分断し、空き台枠は分断しない（台枠として数える）。欠番は位置不明として隣接を作らない。対面（across_aisle）は CSV から一意に決まらないため手動登録とした（ADR-0009） |
| R9 | 中 | 1 回の観測が複数のスランプ系列（数値系列＋画像推定系列）を持ちうるが、`slump_series` に観測内の系列識別子が無い | `series_key` と `derived_from_series_id` を追加。`UNIQUE(source_observation_id, series_key)` |
| R10 | 低 | §3.3「イベント ID が無ければ安定した系列キー」の具体化 | `bonus_events.event_key` = 取得元 ID、無ければ内容ハッシュ＋同一内容内の出現回数。前回系列が今回系列の先頭と一致しない場合は `BONUS_ORDER_CHANGED` を起票 |
| R11 | 低 | §2「UUIDv7 を利用できる場合に採用」: PostgreSQL 16 と Python 3.13 標準ライブラリに生成関数が無い | アプリ側で RFC 9562 準拠の UUIDv7 を生成（ADR-0003） |

| R13 | 低 | §4.2 原本の「変更不可」、§5-4 の「追記専用」を DB で担保する手段 | 原本・観測・系列・改訂の各テーブルに UPDATE/DELETE 禁止トリガーを付けた。保守時のみ `SET slot_data.allow_destructive = 'on'` で解除できる |
| R14 | 低 | §4.4 公開済み配置版を不変にすると、後続版公開時に前版の `valid_to` を確定できない | トリガーで `valid_to` の NULL→日付の 1 回だけを許可（ADR-0009） |
| R15 | 低 | §6-6「台番号の正規化」の規則 | NFKC・空白除去・末尾「番」除去・数字のみなら先頭ゼロ除去。原文は `source_machine_number` に保持 |

## 2. 未決定事項（ユーザー判断が必要）

| # | 重大度 | 事項 | 選択肢 | 推奨 | 影響 |
|---|---|---|---|---|---|
| Q1 | 高 | 両サイトの自動取得 | (a) 手動インポートで運用 (b) 運営者に許可・データ提供契約を打診 (c) 他の許諾済みデータ源を追加 | (a) で運用を始め、並行して (b) を打診 | 許可が得られるまでは自動収集の頻度・網羅性が人手に依存する。許可が得られたら、許可された方式に合わせて Phase 5 を実装する（現状は推測で実装しない） |
| Q2 | 中 | final 判定の `settle_hours` | 12h / 24h / 48h / 手動確定のみ | 24h（設定で変更可） | 後日訂正の多い取得元では長めが安全 |
| Q3 | 中 | 取得元の優先度 | P's CUBE 優先 / 台データオンライン優先 / 店舗ごとに切替 | P's CUBE=10, 台データ=20, 手動=50（設定で変更可） | 採用値の出典が変わる。値の食い違いは常に記録される |
| Q4 | 低 | 原本の保存先 | ローカル FS / S3 互換ストレージ | 初期はローカル FS（`RawStore` を実装すれば差し替え可） | バックアップ手順が変わる |
| Q5 | 低 | 配置 CSV の島端（sequence_no の基準端）の書き方 | 島ごとに注記 / 店舗共通ルール | 店舗共通ルール＋例外を notes に記録 | 背中合わせ判定の正しさ |
